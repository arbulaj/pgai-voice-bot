# Architecture

The bot uses Twilio Programmable Voice to place an outbound call from one fixed Twilio number to the assessment number. When the call is answered, Twilio executes TwiML that opens a **bidirectional Media Stream** to a local FastAPI/WebSocket service exposed through ngrok. The service forwards the practice agent's G.711 µ-law audio to OpenAI Realtime and streams the model's synthesized G.711 µ-law audio back to Twilio. OpenAI Realtime is prompted as a realistic patient using scenario-specific goals, constraints, stressors, and success criteria. Server-side voice activity detection controls turn boundaries, while Twilio `clear` events allow queued patient audio to be interrupted when necessary. Twilio separately records the real phone call in dual-channel mode, and each run produces a matching MP3 recording, transcript, and event log for later analysis.

I chose Realtime speech-to-speech instead of a speech-to-text → text LLM → text-to-speech pipeline because conversational quality and latency are central to this challenge, and a chained pipeline would introduce additional processing at every turn. I also chose a small local FastAPI service plus ngrok rather than deploying infrastructure because it kept the six-hour challenge setup simple while still supporting real phone calls and WebSockets. After the first successful call, I noticed roughly 3–5 second conversational pauses, so I reduced the server-side VAD silence threshold from 650 ms to 400 ms and added timestamps around speech detection, response creation, and audio generation. Later calls felt noticeably faster, while the instrumentation showed generated audio beginning roughly 400 ms after the remote turn ended. I kept automated analysis separate from the final bug report so AI-generated findings could be manually verified against the recordings and transcripts, and I hard-allowlisted the assessment destination to prevent accidental calls to other numbers.
